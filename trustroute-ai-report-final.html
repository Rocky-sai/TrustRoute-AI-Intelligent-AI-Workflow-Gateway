TrustRoute

AI coding tools cost most when the request is not understood: the model guesses, the code fails, and the team pays again. TrustRoute understands the request first, tries a cheaper model, verifies the result, and pays for a stronger model only when a check fails. It works across areas, not just code.

1. The problem and where things stand

Four problems appear when AI tools spread across thousands of people: every request costs the same, AI code is not automatically correct, nobody sees the waste, and one provider is one point of failure. They feed each other, which is why cost and rework rise together.

The real problems

Four problems show up as soon as AI coding tools spread across thousands of people.

Every request costs the same

Most tools send each prompt to one strong model, even a trivial one. Infosys’s CEO has said token cost is now critical for its clients.

AI code is not automatically correct

Models can invent packages, leave insecure patterns or leak keys. Infosys reports over 80,000 delivery staff using AI coding tools and 28 million AI-generated lines of code (company-reported), so checks must be automatic.

Nobody sees the waste

A monthly token total does not show which tasks burn money, or whether the output was ever accepted.

One provider is one point of failure

Price changes, outages and sending proprietary code to a cloud all become business risks.

Why the problem compounds

The four problems feed each other, and each step makes the next one more likely.

More AI-written codeNot every line gets reviewedErrors and fake packages reach buildsRework and late projectsThinner margins, slower growth

Public signals show the same pressure. On its Q1 FY27 call Infosys said AI is compressing some contract values and that one terminated project cost 40 basis points of margin in the quarter. TrustRoute does not claim to cause or cure those events. It removes avoidable waste inside the same margin: tokens paid for easy work, and hours spent fixing code that a check would have caught.

3. The core idea: understand the request first

The cheapest improvement is not a new model. A model given a clear request needs fewer retries and gives better answers, so TrustRoute adds a cheap understanding step in front of any model. It checks length, vagueness, missing context, intent, domain and difficulty, and asks one question when it cannot tell.

Because this layer sits in front of every model and every area, one set of understanding rules serves code, data, banking, IT operations and documents. Adding an area means adding a domain pack, not training a new model.

The proposed solution and its workflow




A thin layer sits between the developer (or agent) and the models. It plugs into tools people already use, by changing a base URL or wrapping one client.


    

  1. Request arrivesSecrets are removed. A repeat question is answered from cache.
    2. 

  2. Cheap model firstA local or company small model tries tasks it can likely handle.
    3. 

  3. Code Guard checksSyntax, security scan, fake packages, secrets, tests.
    4. 

  4. Pass: returnThe developer gets the code and a note on how strongly it was verified.
    5. 

  5. Fail: escalateA stronger model retries, told why the first attempt failed.
    6. 



Existing gateways route without checking the answer. Existing scanners check the answer without choosing the model. TrustRoute joins the two, so spending follows evidence. A vague prompt, such as a typo for “hi”, gets a one-line question instead of a guess, which saves a wasted generation.


Decision rules are set per project: the risk score that counts as a pass, the maximum number of escalations, and whether a failed guard blocks the output (fail closed) or lets it through with a warning (fail open). Medium-risk results go to a human review queue. Every attempt is logged.

Where it fits in the Infosys stack


TrustRoute does not replace Topaz Fabric, the Responsible AI Toolkit or Infosys’s own models. It sits between the teams and the models they already use, and adds the cost and code checks that no single piece covers.





The full platform around TrustRoute


TrustRoute is the gateway, router and verification core (teal outlines). Around it sit the layers a delivery platform needs: retrieval that grounds the model in the client’s code, templates, human checkpoints and a feedback loop.




A failed check returns structured error feedback to the router, which escalates with a capped number of retries. Human review depth is sized by a risk score from change size, blast radius, test coverage and security findings. Checkpoints: acceptance criteria before generation, plan approval for multi-file changes, change review after verification, security sign-off for high-risk areas, and developer takeover when the retry cap is hit.


Every rejected or reworked change is tagged with a cause (missing context, wrong model, bad template, logic error). Weekly fixes update templates, retrieval sources and router thresholds, and a frozen evaluation suite must pass before any change goes live.



Try the Code Guard


Edit the AI-written snippet and run the checks. Checks run cheapest first, so a bad draft is rejected before any expensive retry. This demo uses simple pattern checks and a short list of known packages; the real Code Guard adds a package-index lookup, security scanners and sandboxed tests.

8. Conclusion: the whole picture
The problem. AI tools are used widely, but requests are often unclear, every request goes to the strongest model, code is checked late, and nobody sees where tokens go. Cost, rework and risk rise together, and one provider carries all the dependency.


The situation. Infosys already has model choice through Topaz Fabric, domain small models, responsible-AI guardrails and strong coding agents. What is missing is one governed layer that understands the request, picks the right model, verifies the result and records the cost. The Ask Leon example shows even the first step, understanding a short message, has room to improve.


The solution. TrustRoute is that layer. It does not build a new model. It improves how well requests are understood, so any model performs better, then routes, verifies and records. It is domain-general: packs, not new models, extend it to new areas.
